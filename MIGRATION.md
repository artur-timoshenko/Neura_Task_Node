# Перенос данных в самостоятельный проект

ZIP с исходниками не содержит вашу рабочую базу, пароли пользователей, загруженные
файлы или содержимое localStorage. Новая схема не копирует эти данные автоматически.

## Если Supabase уже находится в вашем собственном аккаунте

Можно оставить тот же проект: задачи, пользователи, роли, чаты и Storage остаются
на месте. Примените только database/upgrade-existing.sql, подключите новые сервисы
и настройте независимый SMTP. После проверки отключите старые Edge Functions,
Send Email Hook и Telegram jobs. Удаление старых функций — отдельная операция в старой
инфраструктуре; локальное удаление файлов не снимает их с публикации.

## Если база принадлежит прежнему облаку

Создайте Supabase в своём аккаунте. Получите экспорт из старого проекта через его
штатный доступ: public/private schema и данные, Auth-пользователи/идентичности, Storage.
Если у вас нет доступа к Auth-экспорту или connection string, один архив кода не
позволяет восстановить аккаунты и пароли. Нужен экспорт у владельца облака.

Для PostgreSQL-доступа используйте официальный процесс
[Backup and Restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore).
Сохраняйте UUID пользователей: на них ссылаются задачи, роли, чаты и участники.
Перенос CSV только из public не сохраняет пароли и Auth identities.
Не переносите прежние remote HTTP cron, Send Email Hook, Vault-секреты или конфиг Edge Functions.

Два допустимых пути:

1. Восстановить проверенный полный дамп приложения/пользователей в пустой проект,
   затем применить database/upgrade-existing.sql. Не запускать install-new.sql.
2. Выполнить database/install-new.sql и отдельно перенести совместимые данные с
   сохранением UUID/связей. Конкретный порядок импорта зависит от вашего экспорта;
   INSERT/COPY в auth.users запускает триггер создания profiles, это нужно учитывать.

Созданные файлы не запускают импорт или изменение старой базы автоматически.
На время переноса остановите изменения в старом приложении, чтобы получить согласованный снимок.

## Файлы Storage

Дамп PostgreSQL не содержит сами бинарные файлы. Скопируйте содержимое bucket
`task-files`, `guide-files`, `avatars`, `company-assets`, сохраняя пути.
Для доступных через Storage API проектов в backend есть scripts/copy-storage.mjs.
В локальный .env дополнительно внесите SOURCE_SUPABASE_URL и SOURCE_SERVICE_ROLE_KEY.
Переменные SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY относятся к целевому проекту.

```powershell
node --env-file=.env scripts/copy-storage.mjs
node --env-file=.env scripts/copy-storage.mjs --copy
```

Первая команда только считает исходные объекты. Вторая копирует без удаления
источника и без перезаписи существующих файлов. При конфликте она останавливается;
после частичного переноса требуется проверить уже перенесённые объекты.
Для больших хранилищ предпочтительнее штатный экспорт/перенос провайдера.

После копирования отредактируйте два адреса в database/rebase-public-assets.sql и
выполните его: так старые аватары и логотип перестанут ссылаться на старый домен.
Приватные вложения задач/гайдов получают новые подписанные ссылки по сохранённому пути.
Пользовательские внешние URL не переписываются автоматически: проверьте такие ссылки
в описаниях, гайдах и проектах отдельно.

## Projects из браузера

В самой ранней версии Projects хранились в localStorage старого домена.
Экспортируйте каждый проект в JSON через старый интерфейс до выключения сайта.
В предыдущей backend-версии они уже находятся в hub_projects: переносите эту таблицу.

Для JSON-экспорта в backend .env укажите APP_URL=адрес нового frontend и
IMPORT_ACCESS_TOKEN=собственный действующий JWT администратора/тимлида.
Не публикуйте токен и удалите его из .env после импорта.

```powershell
node --env-file=.env scripts/import-project.mjs project.json
```

Импорт проходит через проверку доступа backend. Владельцем становится импортирующий
пользователь; историческое авторство комментариев нормализуется на него. Старые UUID
участников должны существовать в новой базе. Автоматического чтения localStorage
чужого домена нет. Экспорт JSON в интерфейсе сохранён.

## Переключение

На временном домене проверьте вход существующих пользователей, восстановление пароля,
роли, создание/редактирование задач, Projects, файлы, оба чата, Realtime, статистику,
гайды, настройки и Telegram. Затем переключайте рабочий домен и APP_URL.
Сессии могут потребовать повторного входа; при смене Supabase-проекта токены старого
проекта больше не действуют. Старую базу и Storage сохраняйте до проверки результата.
